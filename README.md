# VALERIA

**Smart Greenhouse Environmental Intelligence**

VALERIA is an academic, website-based greenhouse monitoring application. It presents current and historical environmental readings, generates threshold alerts and irrigation recommendations, and demonstrates authenticated data ingestion and real-time updates.

> **Current scope:** Readings are generated by a software simulator. No physical sensors are connected. Irrigation is a persisted recommendation/state only; the application does not control a pump, GPIO pin, or other hardware.

## Project overview

### Problem and objectives

Greenhouse operators need a clear view of changing environmental conditions and a way to inspect trends and respond to threshold events. VALERIA demonstrates a full-stack approach to collecting, validating, storing, and presenting that information.

- Show current temperature, humidity, soil moisture, and light measurements.
- Persist sensor readings and greenhouse records in PostgreSQL.
- Generate greenhouse-scoped alerts from configured measurement thresholds.
- Provide moisture-based irrigation recommendations.
- Deliver authorized reading, alert, and irrigation updates to the website in real time.
- Keep simulated data separate from a future physical-device integration.

### Features

- Public landing page, user registration, sign-in, protected pages, and logout.
- Dashboard and live monitoring views for environmental readings, zones, sensor status, alerts, and recommendations.
- Historical analytics over 24-hour, 7-day, and 30-day ranges.
- Sensor inventory and alert history.
- Greenhouse and account settings.
- Alert threshold evaluation, duplicate suppression, recovery handling, and sensor-offline status.
- Direct simulator ingestion or authenticated MQTT ingestion through shared validation and persistence.
- JWT-authenticated, greenhouse-scoped Socket.IO updates.

## Technology and architecture

| Layer | Technologies |
| --- | --- |
| Website | React, TypeScript, Vite, React Router |
| API | Node.js, Express, TypeScript |
| Database | PostgreSQL, Prisma |
| Authentication | bcryptjs password hashing, signed JWT bearer tokens |
| Messaging | MQTT.js, Mosquitto |
| Real-time delivery | Socket.IO |
| Tests and quality | Node test runner through `tsx`, TypeScript, Oxlint |

```text
Stateful simulated sensors
        |
        +--> direct ingestion
        |
        +--> authenticated MQTT broker
                    |
Express API and shared validation/ingestion services
                    |
         Prisma transactions -> PostgreSQL
                    |
      alert and irrigation evaluation
                    |
 REST responses + authenticated Socket.IO events
                    |
               React website
```

The MQTT path is suitable as a future integration point for a device such as an ESP32 or Arduino, but support for that path does not mean physical hardware is installed or connected.

### Frontend

`client/src` contains the public and authentication pages, protected application pages, shared components/layout, API services/hooks, and Socket.IO client. `VITE_API_BASE_URL` configures the API base path; `VITE_SOCKET_URL` optionally selects a Socket.IO origin. During local development, Vite proxies `/api` and `/socket.io` to `VITE_API_PROXY_TARGET`.

### Backend

`server/src` contains the Express server and routes, controllers, authentication and validation middleware, domain services, repositories, Prisma access, simulator, MQTT adapter/protocol, and real-time event delivery. Protected requests use the identity from a verified JWT, and data access is scoped to the authenticated user's greenhouse.

### Database

The Prisma schema is `server/prisma/schema.prisma`; migration files are under `server/prisma/migrations`. The schema defines:

- `User`: account identity and password hash.
- `Greenhouse`: greenhouse owned by a user.
- `SoilZone`: greenhouse area and its irrigation/recommendation state.
- `Sensor`: registered sensor metadata and status.
- `SensorReading`: persisted environmental snapshots.
- `SensorMeasurement`: persisted individual metric measurements.
- `Alert`: greenhouse-scoped alert records and resolution state.

The current schema does not define plant/crop, physical-device, or irrigation-event records. Irrigation recommendation state should not be interpreted as a record of physical water delivery.

## Authentication and security

- Passwords are hashed with bcryptjs; password hashes are not returned by the API.
- Protected HTTP routes and Socket.IO connections require a valid JWT.
- The server determines the authorized greenhouse room for Socket.IO; clients cannot choose arbitrary rooms.
- MQTT broker authentication and topic ACLs are used in MQTT mode. The backend also validates the greenhouse/sensor relationship, topic, payload structure, metric, timestamp, and accepted value bounds before ingestion.
- CORS uses the configured `CLIENT_URL`; requests without an `Origin` header are also accepted (for example, non-browser clients). Set the allowed origin deliberately before deployment.
- Browser JWTs are held in local or session storage. Logging out clears the browser-side token; it does not revoke an already-issued JWT on the server.
- Keep `.env` files, MQTT passwords, and broker password/ACL files private. Never commit actual secrets.
- For network-exposed deployments, use HTTPS and MQTT over TLS (`mqtts://`), strong unique secrets, firewall restrictions, and a secured/managed database.

The workspace ignores `.env` and `.env.*` files except `.env.example`, as well as `node_modules` and build outputs. The delivered workspace may not include Git metadata, so confirm ignore and version-control behavior in the actual checkout before publishing.

## Local setup

Open PowerShell in the project root. Install the two application packages:

```powershell
npm install --prefix client
npm install --prefix server
```

Create `server/.env` from `server/.env.example` and `client/.env` from `client/.env.example`. Use local values in these ignored files; do not put credentials in this README. Configure `DATABASE_URL` for a running PostgreSQL instance, then generate the Prisma client and apply committed migrations:

```powershell
npm --prefix server run prisma:generate
npm --prefix server run prisma:deploy
```

The seed command is intended for an empty/fresh development database. Review `server/prisma/seed.ts` before running it. Do not run a seed against data you need to preserve without reviewing its behavior and making a backup. Do not use `prisma migrate reset` for a database containing data that must be kept.

## Running VALERIA

Run the backend and website in separate PowerShell terminals from the project root.

Terminal 1 (API; in development the simulator starts with the server and sends through the configured direct or MQTT input mode):

```powershell
npm run server:dev
```

Terminal 2 (Vite website):

```powershell
npm run dev
```

Open the local URL printed by Vite, normally `http://localhost:5173`. The API health endpoint is `http://localhost:5000/api/health`.

For MQTT simulator mode, configure the local Mosquitto service, its authenticated account, and greenhouse-scoped ACLs first; set `SENSOR_INPUT_MODE=mqtt` and the corresponding `MQTT_*` values in `server/.env`. Never overwrite an existing broker password file or recreate an existing account as part of routine setup. In particular, do not run a password-file creation command with `mosquitto_passwd -c` against an existing password file. Confirm the installed broker configuration and service state before relying on MQTT security.

In production, build the client and server, then start the compiled server and serve the built client using the chosen web server/reverse proxy:

```powershell
npm run server:build
npm run build
npm run server:start
```

The in-process simulator is disabled in production. Supply readings through an external producer (for example, an authorized MQTT publisher) if production ingestion is required.

## MQTT ingestion

The backend subscribes to greenhouse-scoped topics:

```text
valeria/greenhouses/<greenhouseId>/readings
valeria/greenhouses/<greenhouseId>/sensors/<sensorId>/reading
```

Incoming messages are limited to 16,384 bytes and must be valid JSON objects with recognized identifiers, metric/value data, and valid timestamps. Topic IDs and sensor-to-greenhouse ownership are checked before the shared reading ingestion path writes data. Configure Mosquitto to require authentication and restrict each publisher to only its authorized greenhouse topics. Broker ACLs and application-level checks are complementary, not interchangeable.

The workspace includes broker configuration under `server/mosquitto/`. Review the configuration and referenced paths for the installed machine before applying it. Protect any existing Mosquitto password file and account; avoid scripts or commands that create/replace a password file when preserving existing credentials.

## Real-time updates

The server emits greenhouse-authorized Socket.IO events:

- `sensor:reading`
- `alert:created`
- `alert:updated`
- `alert:resolved`
- `irrigation:updated`

The website receives updates over its authenticated Socket.IO connection. REST endpoints remain available for initial page data and history.

## Simulator, alerts, and irrigation behavior

The simulator runs at a default five-second interval in development. In `direct` mode it sends readings through the ingestion service; in `mqtt` mode it publishes readings to the configured broker and they return through MQTT ingestion. Its generated values are stateful: temperature and humidity are correlated and influenced by time of day, soil moisture declines gradually, and light follows day/night variation. The simulator is for demonstrating software behavior and is not a calibrated model of a specific greenhouse.

Measurement bounds and stale-sensor timing can be configured with the `SENSOR_*` environment variables. Greenhouse thresholds drive alert creation, suppression of duplicate active alerts, and recovery behavior. Irrigation uses soil moisture and a two-point recovery margin to represent recommendation state. It does not schedule or operate real irrigation equipment.

## Troubleshooting

- **Website cannot reach the API:** Confirm the server is running, `PORT` and `VITE_API_PROXY_TARGET` agree, and `CLIENT_URL` matches the browser origin.
- **Database connection or Prisma errors:** Verify PostgreSQL is running and `DATABASE_URL` is correct; run `prisma:generate` and apply migrations with `prisma:deploy`. Do not reset a database containing data you need.
- **No new readings in direct mode:** Confirm `SENSOR_INPUT_MODE=direct`, the backend development process is running, and the development simulator has started.
- **No readings in MQTT mode:** Verify the broker URL/port, service status, existing username/password, topic ACL, greenhouse and sensor IDs, and JSON payload validity. Confirm the broker is actually listening with the intended configuration.
- **MQTT authentication fails:** Verify the backend uses the existing account's credentials and that the broker password file was preserved. Do not use `mosquitto_passwd -c` on an existing password file.
- **Real-time page appears stale:** Check the browser's API and Socket.IO connectivity, token validity, and server logs. Reloading should retrieve current persisted data through REST.
- **Sensor is offline:** Check the last accepted reading and `SENSOR_STALE_AFTER_MS`.
- **Seed account is unavailable:** Review the seed script and configured seed-only variables; do not reseed a database with existing data without first checking the script's effects.

## Limitations and future work

Current limitations:

- Sensor measurements are simulated; no physical sensor integration is delivered.
- Irrigation is recommendation/state only; no hardware actuation is implemented.
- Notification preferences are UI/session state; email and push delivery are not implemented.
- Password reset is not implemented.
- Browser logout clears the client token but does not revoke an issued JWT server-side.
- Local development configuration is not a substitute for production TLS, deployment secrets, broker hardening, monitoring, backups, and operational procedures.

Possible future work includes validated physical sensor adapters, secure device provisioning, measured calibration, irrigation hardware integration with safety interlocks, email/push notifications, password reset, token revocation, and deployment monitoring.

## project summary

VALERIA demonstrates a web-based environmental monitoring workflow using a React/TypeScript client, an Express/TypeScript API, PostgreSQL persistence through Prisma, JWT authentication, MQTT ingestion, and Socket.IO updates. The project includes simulated sensor input, historical analytics, threshold-based alerts, and moisture-based irrigation recommendations. Its current implementation is a software prototype: it does not claim physical sensor connectivity, calibrated agricultural predictions, or automated control of greenhouse equipment.
